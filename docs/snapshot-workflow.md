# 项目库快照分析

更新日期：2026-10-14（Asia/Shanghai）。基线分支：`feature/refine-project`。

## 用途与范围

项目库从只读摘要扩展为可复用分析入口。用户显式保存 ZIP 后，刷新浏览器仍可选择已保存的快照，完成 Inspect、Validate、Analyze、源码阅读、证据追问及报告保存，无需再次上传 ZIP。

复用现有 AST、符号解析、调用关系及证据规则；不执行上传代码，不修改源码，不新增语言或影响判断算法。现有直接上传及独立演示流程保持可用。

## 使用流程

1. 上传页选择 `frontend/public/samples/signature_change.zip`。
2. 点击“保存并读取项目”，保存成功后进入函数选择页。
3. 刷新页面，进入工作台，打开侧边栏“项目库”。
4. 选择项目，点击“使用此快照分析”。
5. 选择 `utils.format_date`，新增普通位置或关键字参数 `timezone`。
6. 点击“校验变更”，通过后“开始分析”。
7. 查看 `report.py:5` 的 `return format_date(date)` 证据，可打开完整源码。
8. 可点击“下载 JSON”保存完整报告内容，用于交接或证据复核。
9. 点击“保存到历史”，在历史报告中读取结果。
10. 历史报告点击“打开来源项目”，回到该快照的目标选择页，可重新配置变更。

预期：Direct=1、1-hop=1、2-hop=1，覆盖 complete。来源是保存的真实 ZIP；前端没有浏览器 File 也能完成第 4 至 8 步。

## 接口与数据来源

上传保存使用 `POST /api/v1/projects`。后续使用 `POST /api/v1/snapshots/{snapshot_id}/{operation}`，operation 为 `inspect`、`validate`、`analyze`、`reports`、`source`、`questions` 或 `question-suggestions`。字段和错误码见 [API 契约](api-contract.md#复用快照)。

- ID 用于查询已保存快照；SHA-256 用于核对 ZIP 字节，两者用途不同。
- 文件名和源码根目录由保存记录提供，请求不能覆盖服务器路径或根目录。
- 同名项目重复保存会追加新的快照版本；项目最新更新时间和最新快照指向最近一次保存。
- 每次使用前检查快照目录边界、普通文件、大小和指纹，再执行现有安全解包流程。
- 文件丢失、损坏或指纹不匹配时明确失败，不返回演示结果。重新上传相同 ZIP 可以修复已损坏的普通快照文件。
- 切换快照或上传另一份 ZIP 时清空旧选择、校验和报告，迟到请求不能覆盖新状态；源码缓存和追问跟随项目身份切换。
- 从快照保存的完整报告包含 `project_id` 和 `project_snapshot_id`。没有新增报告表关联列或按项目筛选 API。
- 原 `inspect`、`validate`、`analyze` 上传端点的请求与响应保持原契约。
- 本地分析任务基础已存在：`POST /api/v1/analysis-tasks` 可基于已保存快照创建任务，后端记录 queued/running/succeeded/failed，并在成功后保存报告 ID。前端可只读查看任务列表和详情；当前主流程仍直接调用快照 Analyze/Reports 接口，还没有把“开始分析”切换为任务轮询、自动重试或独立 worker。

## 当前限制

- 登录页仍为演示入口，没有用户隔离；项目库属于本机工作台。
- 同名项目会追加新的快照版本；自动保留策略尚未实现。
- 本机项目和快照可手动删除；删除不级联删除历史报告，也不代表账号级项目权限管理。
- 刷新后需要从项目库重新选择快照，不自动恢复未保存的变更草稿。
- 历史报告可直接阅读、下载 JSON 并打开关联来源快照；不会自动恢复旧的变更草稿或分析会话。完整源码和追问需在来源项目中重新分析后使用，未关联快照的旧报告不提供猜测性的跳转。
- 快照分析主流程仍是同步请求；已有本地任务 API 和只读任务状态页，但未把“开始分析”接入任务轮询、自动重试或生产级后台队列。
- SQLite 和 ZIP 文件均需保留。修改快照目录配置不会自动迁移旧文件；实际文件位置见 [数据库说明](database.md)。
